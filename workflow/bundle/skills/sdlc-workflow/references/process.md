# Stage and evidence contract

0. Discover product purpose and MVP; present them in chat and record the user's decision with `decision.accept`. Propose architecture, application structure, implementation/test standards, autonomous boundaries and delivery; present them in chat and record acceptance. Bootstrap operations, CI, test tooling and artifacts; verify fresh checkout/recovery, then create a ready PR for the user to merge manually.
1. Retrieve context from the user's description. Author requirements with stable IDs, examples, scope and unknowns, validate them, and present them to the user for chat acceptance.
2. Author observable scenarios and coverage, validate cross-references, and present the exact artifact version to the user for chat acceptance.
3. Plan small vertical increments and bounded tasks, cross-application impact/contracts, dependencies and trigger-based verification. Validate the executable plan and obtain the user's chat acceptance before implementation; changed business scope or foundations also require an explicit user decision.
4. For the next increment, author readable tests and realistic fixtures, establish behavioral RED, and record its verified evidence. Workflow checks complete tasks when current verification and a pushed scoped checkpoint pass; no separate task review is required.
5. Implement task by task in short RED/GREEN/refactor loops. Return to 4 for new/corrected tests. Commit and push each completed task checkpoint, then advance increments after their verified tasks pass. At feature completion, update documentation, inspect the full diff, run acceptance, create a ready PR, and let the user merge it manually. Wait for GitHub to confirm the merge before completing the change.
6. Build source-bound artifacts, publish private container images, verify exact published digests and system collaboration, promote a compatible release set without rebuilding, deploy locally and verify behavior.

Defects require expected behavior, reproduction and verified regression RED, plus the user's chat acceptance of the defect report. File-changing FEATURE and MAINTENANCE increments use verified behavioral RED before implementation; a MAINTENANCE plan with `outcome: NO_FILE` instead requires current GREEN evidence and empty file ownership for its test-author and implementer tasks. Workflow changes follow the pinned active workflow, use dedicated branches and evaluations, and do not activate merely by merging. Changes remain pinned unless an explicit migration is verified.

Task, increment, feature integration, publication, artifact verification, release, deployment and deployment verification are distinct states. Gate advancement is controller-owned. Executable stage policies cover project initialization, feature requirements and plan acceptance, feature increment completion/integration, and defect reproduction/completion. `stage.inspect` and `stage.advance` validate product/architecture gates through bootstrap merge, feature requirements/scenario coverage and accepted implementation-plan coverage, and bugfix report/reproduction plus verified test-author RED before implementation. Feature tasks are bound to the accepted plan; `increment.inspect`/`increment.advance` allow only the next increment after its verified task results and current RED/GREEN evidence. FEATURE and BUGFIX implementer tasks must depend on evidence-backed RED test-author tasks. Business approvals are recorded from explicit user decisions in chat. The user performs GitHub PR review and merge manually; stage completion only verifies the merged PR state and records a receipt. Publication, candidate verification, release, and local deployment remain separate receipt-backed operations.

Respect registered operation timeouts and test-profile limits. Human workflow decisions happen in chat against the inspected artifact version; task completion follows recorded verification evidence and a pushed checkpoint. Resume from durable state and reconciled external effects, not conversation memory.
