# Stage and evidence contract

0. Discover product purpose and MVP; review and obtain product acceptance. Propose architecture, application structure, implementation/test standards, autonomous boundaries and delivery; review and obtain architecture acceptance. Bootstrap operations, CI, test tooling and artifacts; verify fresh checkout/recovery, then whole-change review and human merge acceptance.
1. Retrieve context from the user's description. Author reviewed requirements with stable IDs, examples, scope and unknowns.
2. Author observable scenarios and coverage. Review independently, then obtain actual business acceptance bound to exact content.
3. Plan small vertical increments and bounded tasks, cross-application impact/contracts, dependencies and trigger-based verification. Independently review and obtain authenticated acceptance of the executable plan before implementation; changed business scope or foundations also require an explicit user decision.
4. For the next increment, author readable tests and realistic fixtures, establish behavioral RED and obtain independent test review.
5. Implement task by task in short RED/GREEN/refactor loops. Return to 4 for new/corrected tests. Check each task, commit/push changed completed tasks, and review increments. At feature completion, update documentation, review full diff, run acceptance, obtain human acceptance and squash merge.
6. Build source-bound artifacts, publish private container images, verify exact published digests and system collaboration, promote a compatible release set without rebuilding, deploy locally and verify behavior.

Defects require expected behavior, reproduction and reviewed regression RED. File-changing FEATURE and MAINTENANCE increments use reviewed behavioral RED before implementation; a reviewed MAINTENANCE plan with `outcome: NO_FILE` instead requires current GREEN evidence and empty file ownership for its test-author and implementer tasks. Workflow changes follow the pinned active workflow, use dedicated branches and evaluations, and do not activate merely by merging. Changes remain pinned unless an explicit migration is verified.

Task, increment, feature integration, publication, artifact verification, release, deployment and deployment verification are distinct states. Expected RED may checkpoint to a draft PR; required checks must be green before merge. Gate advancement is controller-owned. Executable stage policies cover project initialization, feature requirements and plan acceptance, feature increment completion/integration, and defect reproduction/completion. `stage.inspect` and `stage.advance` validate product/architecture gates through bootstrap merge, feature requirements/scenario coverage and accepted implementation-plan coverage, and bugfix report/reproduction plus reviewed test-author RED before implementation. Feature tasks are bound to the accepted plan; `increment.inspect`/`increment.advance` allow only the next increment after its reviewed task results and current RED/GREEN evidence. FEATURE and BUGFIX implementer tasks must depend on evidence-backed, currently accepted test-author RED tasks, and checkpoints and task results refresh that review. Bugfix completion requires a verified squash-merge receipt. Feature and maintenance change stages end at verified squash-merge completion. Publication, candidate verification, release, and local deployment are separate receipt-backed delivery operations, not additional stage.advance transitions.

Each task review loop is limited to three reviewed attempts. A current authenticated `CHANGES_REQUESTED` review starts a new TDD/checkpoint cycle; the third unresolved review moves the task to `BLOCKED` and must be escalated to the human coordinator. Respect registered operation timeouts and test-profile limits. Codex token/cost/session cancellation controls are host capabilities and must be reported as unavailable until observed. Resume from durable state and reconciled external effects, not conversation memory.
