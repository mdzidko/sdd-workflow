# Operation access

Call `node scripts/workflow/run.mjs OPERATION --project PROJECT_ROOT` with one JSON input object on stdin. Inspect the registry and operation response for its actual supported status, required fields, preconditions and error code. Reuse request IDs where a registered operation supports reconciliation. Do not rewrite operation logic in ad hoc shell commands.

When installing from the cloned workflow source, run `bundle.inspect` and `bundle.preflight`, then call `workflow.setup` with the selected target root. Setup is repeatable, commits only workflow-owned assets on the chosen local base branch, creates no remote, and leaves product state uninitialized. Open the target in Codex, reload if required, and verify `$sdlc-workflow` plus native specialist discovery before starting Stage 0 with `workflow.init` and a validated target profile. Use `workflow.inspect` to inspect initialized state; `workflow.resume` reconciles prior state. context.prepare, repo.search, repo.read and tests.find provide bounded source context. artifact.create/validate and spec.validate/plan.validate handle structures; independent review handles meaning.

Use change.route to retrieve the registered playbook for the persisted change kind. Its result is advisory and cannot advance a stage or authenticate a decision. A verified no-file task can be recorded without an empty commit; consult the route reference for evidence and review requirements.

Task and stage mutations require controller checks. Use stage.inspect to read the current gate and its missing evidence before stage.advance; the operation checks the expected stage and state revision, then refreshes the GitHub PR head and current human decisions. The PROJECT_INIT policy requires valid unchanged product artifacts plus human approval before architecture, and architecture artifacts plus approval before bootstrap; completion additionally requires a recorded squash merge. FEATURE requires schema-valid requirements and scenarios, complete requirement coverage, unchanged content and current authenticated approval before planning. Planning-to-implementation requires a validated implementation-plan artifact covering every accepted scenario, a verification schedule, and current authenticated approval. Each plan increment must include test-author and implementer tasks, and every implementer must directly depend on a test-author task in that increment. Once accepted, feature task IDs, roles, increments, scenarios, dependencies, outputs, and verification profiles must match that pinned plan. Use `increment.inspect` and `increment.advance` to keep work on the next planned increment; advancement refreshes accepted task reviews and requires reviewed RED/GREEN evidence for its test and implementation tasks. `stage.advance` cannot move to integration until every planned increment passes that gate. FEATURE and BUGFIX implementer tasks must directly depend on at least one test-author task with assertion-failure RED evidence and a current accepted human review. A prepared implementer remains in `WAITING_DEPENDENCY` until its dependency is accepted; review resolution unblocks or re-blocks it. The checkpoint and result operations refresh the test review before proceeding. The BUGFIX policy additionally requires an unchanged defect report with expected and observed behavior and reproduction steps before implementation; completion requires a recorded squash merge. `change.cleanup` is available after a verified squash merge. It requires GitHub automatic branch deletion, confirms the remote branch is gone, and removes only the unchanged local PR-head reference after the integration branch contains the merge. The change stage machine ends at verified integration; publication, candidate verification, release, and local deployment are separate receipt-backed delivery operations rather than stage.advance transitions. Their distinct receipts preserve delivery progress without changing the merged change stage. Maintenance uses its reviewed impact map; no-file BUGFIX intent is approved through a linked GitHub Issue, and stage advancement refreshes the latest exact-artifact human decision. WORKFLOW_CHANGE requires a trusted Actions evaluation report imported with evaluation.ingest before integration; activation and migration remain fail-closed. decision.ingest does not accept an agent's actor field or prose as human authority; only configured authenticated evidence can satisfy a human gate. review.resolve checks an actual allowlisted GitHub human review against the task checkpoint history and the task result marker returned by task.record_result. General business decisions still require their own authenticated evidence.

For a `WORKFLOW_CHANGE`, keep using the bundle pinned when the change started. After the reviewed increments finish, dispatch the trusted evaluator from the configured integration branch with the exact current PR head SHA and change ID. Import only its successful retained report using `evaluation.ingest` with the GitHub Actions run ID. The import verifies the workflow path, evaluator commit against the current integration branch, run attempt, unique artifact, report identity, candidate commit, and candidate bundle version. `stage.advance` refreshes the PR head and accepts only that unchanged report. Evaluation permits progression to integration; it never activates a bundle or authorizes migration.

After a process interruption, inspect operation locks before retrying mutations. Recover only a stale lock using the exact ID from `workflow.lock.inspect`; active, unknown, malformed, or changed owners must remain blocked. Never remove a recovery guard based on age alone.

Privileged operations may be deliberately unavailable when credentials, adapters, host capabilities or enforceable permission boundaries are missing. Preserve the returned reason. No JSON field named approved, simulated success or invented URL can replace live proof. External operations require user-authorized scope. Installation is not activation or proof of runtime capability.
