# Operation access

Call `node scripts/workflow/run.mjs OPERATION --project PROJECT_ROOT` with one JSON input object on stdin. Inspect the registry and operation response for its actual supported status, required fields, preconditions and error code. Reuse request IDs where a registered operation supports reconciliation. Do not rewrite operation logic in ad hoc shell commands.

When installing from the cloned workflow source, run `bundle.inspect` and `bundle.preflight`, then call `workflow.setup` with the selected target root. Setup is repeatable, commits only workflow-owned assets on the chosen local base branch, creates no remote, and leaves product state uninitialized. Open the target in Codex, reload if required, and verify `$sdlc-workflow` plus native specialist discovery before starting Stage 0 with `workflow.init` and a validated target profile. Use `workflow.inspect` to inspect initialized state; `workflow.resume` reconciles prior state. context.prepare, repo.search, repo.read and tests.find provide bounded source context. artifact.create/validate and spec.validate/plan.validate validate artifact structure and cross-references; show business artifacts to the user and record acceptance or rejection with decision.accept in chat.

Use change.route to retrieve the registered playbook for the persisted change kind. Its result is advisory and cannot advance a stage or authenticate a decision. A verified no-file task can be recorded without an empty commit; consult the route reference for evidence and review requirements.

Task and stage mutations require controller checks. Use `stage.inspect` to read the current gate and missing evidence before `stage.advance`; supply the inspected stage and state revision. Business decisions are made in chat: present the exact current artifact, wait for the user's explicit approval or rejection, then call `decision.accept` with its inspected content hash and state revision. This immediately records `APPROVED` or `REJECTED` against that artifact content. The PROJECT_INIT, FEATURE, MAINTENANCE, BUGFIX, and WORKFLOW_CHANGE policies require these recorded decisions where specified. Each plan increment still includes test-author and implementer tasks; verified task results do not need a formatted review or reviewer marker. Use `increment.inspect` and `increment.advance` to keep work on the next planned increment and satisfy current RED/GREEN evidence. The user merges the PR manually. When advancing to `COMPLETE`, the workflow refreshes GitHub and records a receipt only if the PR is actually merged; otherwise it reports `MERGE_PENDING` and leaves the stage unchanged. `change.confirm_merge` performs the same confirmation explicitly. `change.cleanup` remains optional guarded cleanup after confirmed merge. Workflow changes still require a trusted Actions evaluation report before integration; activation and migration remain fail-closed.

For a `WORKFLOW_CHANGE`, keep using the bundle pinned when the change started. After the reviewed increments finish, dispatch the trusted evaluator from the configured integration branch with the exact current PR head SHA and change ID. Import only its successful retained report using `evaluation.ingest` with the GitHub Actions run ID. The import verifies the workflow path, evaluator commit against the current integration branch, run attempt, unique artifact, report identity, candidate commit, and candidate bundle version. `stage.advance` refreshes the PR head and accepts only that unchanged report. Evaluation permits progression to integration; it never activates a bundle or authorizes migration.

After a process interruption, inspect operation locks before retrying mutations. Recover only a stale lock using the exact ID from `workflow.lock.inspect`; active, unknown, malformed, or changed owners must remain blocked. Never remove a recovery guard based on age alone.

Privileged operations may be deliberately unavailable when credentials, adapters, host capabilities or enforceable permission boundaries are missing. Preserve the returned reason. No JSON field named approved, simulated success or invented URL can replace live proof. External operations require user-authorized scope. Installation is not activation or proof of runtime capability.
